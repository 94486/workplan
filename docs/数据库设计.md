# 数据库设计

> 本文档说明 WorkDashboard（龙猫工作统计台）的 SQLite 数据库结构、设计决策与权衡、完整性与迁移策略，以及数据文件的存放与打包保留规则。对应实现见 [`backend/database.py`](../backend/database.py)（建表 DDL 与连接层）与 [`backend/models.py`](../backend/models.py)（Pydantic 入参校验）。

## 设计目标

- **本地优先、零配置**：单个 `.db` 文件即全部数据，无需安装任何数据库服务，可随文件夹整体拷贝 / 备份 / 迁移。
- **简单可靠**：标准库 `sqlite3`，每个操作使用独立短连接（用完即关），规避多线程共享连接问题，适配 FastAPI + Uvicorn 的请求模型。
- **两套薪资模式彻底隔离**：日薪与月薪使用各自独立的表，切换模式互不干扰、互不污染数据。
- **外部数据先进「待审查箱」再入库**：推送不直接写正式表，保证用户对本机数据的完全掌控。

## 表结构总览

| 分组 | 表 | 用途 |
| --- | --- | --- |
| 日薪模式 | `works` | 工作任务（含预期 / 实际收入） |
| 日薪模式 | `presets` | 录入预设（按 `work_type` 独立） |
| 月薪模式 | `monthly_works` | 工作任务（**无收入字段**） |
| 月薪模式 | `monthly_presets` | 录入预设（独立于日薪预设） |
| 月薪模式 | `monthly_settings` | 月度收入配置（单行） |
| 数据对接 | `push_config` | 对接码（单行） |
| 数据对接 | `push_inbox` | 待审查箱（推送 JSON 快照） |

## 完整 DDL

建表语句为幂等的 `CREATE TABLE IF NOT EXISTS`，首次启动自动执行。

```sql
-- ===== 日薪模式 =====
CREATE TABLE IF NOT EXISTS works (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    name          TEXT    NOT NULL,                    -- 工作名称
    work_type     TEXT    NOT NULL DEFAULT 'regular',  -- regular=常规 / other=其他
    duration_hours REAL   NOT NULL DEFAULT 0,          -- 花费时长(小时, 计划)
    planned_date  TEXT    NOT NULL,                    -- 计划完成日期 YYYY-MM-DD
    expected_income REAL  NOT NULL DEFAULT 0,          -- 预期收入(元)
    notes         TEXT    NOT NULL DEFAULT '',         -- 备注
    status        TEXT    NOT NULL DEFAULT 'pending',  -- pending=待完成 / done=已完成
    actual_duration_hours REAL,                        -- 实际花费时长(小时)
    completed_date TEXT,                               -- 完成日期 YYYY-MM-DD
    actual_income REAL,                                -- 实际收入(元)
    created_at    TEXT    NOT NULL,
    updated_at    TEXT    NOT NULL
);

CREATE TABLE IF NOT EXISTS presets (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL, work_type TEXT NOT NULL DEFAULT 'regular',
    duration_hours REAL NOT NULL DEFAULT 0, expected_income REAL NOT NULL DEFAULT 0,
    notes TEXT NOT NULL DEFAULT '', created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);

-- ===== 月薪模式（与日薪完全隔离；任务无每日收入字段） =====
CREATE TABLE IF NOT EXISTS monthly_works (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL, work_type TEXT NOT NULL DEFAULT 'regular',
    duration_hours REAL NOT NULL DEFAULT 0, planned_date TEXT NOT NULL,
    notes TEXT NOT NULL DEFAULT '', status TEXT NOT NULL DEFAULT 'pending',
    actual_duration_hours REAL, completed_date TEXT,
    created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS monthly_presets (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL, work_type TEXT NOT NULL DEFAULT 'regular',
    duration_hours REAL NOT NULL DEFAULT 0, notes TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);

-- 单行配置：CHECK(id = 1) 保证全库仅一条收入口径记录
CREATE TABLE IF NOT EXISTS monthly_settings (
    id INTEGER PRIMARY KEY CHECK (id = 1),
    month_key TEXT NOT NULL DEFAULT '',           -- 对应月份 YYYY-MM
    regular_income REAL NOT NULL DEFAULT 0,       -- 上月常规收入
    other_income   REAL NOT NULL DEFAULT 0,       -- 上月其它收入
    updated_at TEXT NOT NULL
);
-- 注：total_income 由后端在响应中计算返回，不落库。

-- ===== 数据对接 =====
CREATE TABLE IF NOT EXISTS push_config (
    id INTEGER PRIMARY KEY CHECK (id = 1),
    api_key TEXT NOT NULL, updated_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS push_inbox (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    payload TEXT NOT NULL,                          -- 完整推送 JSON 快照（含 source/pushed_at/data）
    record_count INTEGER NOT NULL DEFAULT 0,        -- 可识别记录数（供界面展示）
    status TEXT NOT NULL DEFAULT 'pending',         -- pending / merged / discarded
    received_at TEXT NOT NULL, merged_at TEXT
);
```

## 索引

| 表 | 索引 | 支撑的高频查询 |
| --- | --- | --- |
| `works` | `idx_works_planned_date` | 看板按日期区间取任务、周/月汇总 |
| `works` | `idx_works_status` | 待办 / 已完成筛选、逾期统计 |
| `works` | `idx_works_work_type` | 常规 / 其他分类统计 |
| `presets` | `idx_presets_work_type` | 按类型加载预设 |
| `monthly_works` | `idx_mworks_planned_date` / `idx_mworks_status` / `idx_mworks_work_type` | 同 `works`（月薪侧） |
| `monthly_presets` | `idx_mpresets_work_type` | 按类型加载月薪预设 |
| `push_inbox` | `idx_push_inbox_status` | 待审查箱按 `status=pending` 拉取 |

索引只建在**真正参与过滤 / 分组**的列上，避免过度索引拖慢写入——对个人工作台的写入频率而言，这组索引足够且开销极小。

## 关键设计决策与权衡

- **日薪 / 月薪分表，而非用 `mode` 列区分**：两套数据在产品语义上"完全独立、互不干扰"。分表让隔离由数据库结构天然保证，避免"忘记带 mode 过滤"导致的数据串味，也让月薪表可以省略收入字段（`monthly_works` 无 `expected_income` / `actual_income`）。代价是表数量翻倍、部分 CRUD 逻辑重复，换来的是清晰与低出错率——对本地单用户场景是正确取舍。
- **日期用 `TEXT` 存 ISO `YYYY-MM-DD`**：SQLite 无原生日期类型，ISO 8601 字符串可按字典序正确比较与范围查询（`>= / <=`），且导入导出、跨语言读取零歧义。
- **金额用 `REAL`**：个人记账场景，金额上限 1000 万、两位小数，`REAL` 足够；未采用"分为单位的整数"是为了与前端 / CSV 直接读写保持简单。若未来对分账精度有强要求，可迁移为整数分。
- **单行配置用 `CHECK(id = 1)`**：`monthly_settings` / `push_config` 逻辑上是"全局唯一一条"，用主键约束把"单例"固化进结构，杜绝脏数据多行。
- **待审查箱存 `payload` JSON 快照**：外部推送结构多变，逐字段拆列会造成表膨胀与频繁迁移；整包快照 + 少量可查询列（`record_count` / `status`）既保留原始证据、又满足"待审查 / 已合并 / 已丢弃"的状态流转。识别字段 `source` / `pushed_at` 仅随快照展示，不入库、不参与统计。
- **短连接 + `row_factory = sqlite3.Row`**：每次操作独立连接、返回 `dict`，代码简单、无跨请求状态，契合无状态 HTTP 层。

## 数据完整性与校验

- **入参校验在应用层（Pydantic）**：`models.py` 对名称（非空 / 去空格 / 长度 ≤ 100）、`work_type`（枚举 `regular|other`）、`status`、日期（`date.fromisoformat` 解析）、数值（`ge=0` 且设上限）做了严格校验；月薪模型用 `extra="forbid"` 拒绝误传收入字段，进一步保证两套数据隔离。
- **可选加固（非缺陷）**：`work_type` / `status` 目前只在应用层约束，可在建表时追加数据库级 `CHECK (work_type IN ('regular','other'))` 与 `CHECK (status IN ('pending','done'))`，防止绕过 API 的直接写库产生脏值。当前 API 是唯一写入路径，故非必需。
- **外键**：各表相互独立，无外键关系；连接层仍开启 `PRAGMA foreign_keys = ON`，为未来可能的关联预留。

## 迁移与幂等

- `init_db()` 以 `CREATE TABLE IF NOT EXISTS` 建表，重复启动安全。
- `_migrate()` 做轻量兼容：用 `PRAGMA table_info` 探测并清理旧版 `push_inbox` 遗留的独立列（`source` / `pushed_at` / `device` / `username`），DROP 失败（旧版 SQLite 不支持）则忽略、空列保留不影响功能。
- 演示数据仅在 `works` 为空且 `SEED_DEMO=1` 时写入，不会污染已有数据。

## 数据文件位置与打包保留

数据库路径解析见 `get_db_path()` / `get_project_root()`：

| 运行方式 | 数据文件位置 |
| --- | --- |
| 源码运行 | 仓库根目录 `data/works.db` |
| PyInstaller 打包 exe | **exe 同级** `data/works.db`（如 `dist/data/works.db`），而非临时解包目录，避免退出即清空 |
| Docker | 环境变量 `WORK_DB_PATH`（默认映射 `/data/works.db` 卷） |

- `WORK_DB_PATH` 环境变量优先级最高，可将数据指向任意路径。
- **重新打包不丢数据**：`build_exe.bat` 在构建前把 `dist\data\works.db` 备份到 `_db_backup.tmp`，构建完成后还原；PyInstaller 只重建 `dist\WorkDashboard.exe`，不触碰 `dist\data\`。
- ⚠️ **注意**：exe 读取的是 `dist/data/works.db`，与源码运行用的仓库 `data/works.db` 是**两个文件**。若你平时从源码开发（数据在仓库 `data/`），首次使用 exe 前需把该文件复制到 `dist/data/works.db`，否则 exe 会看到另一份（或空）数据。

## 备份与恢复

- **应用内导出**：「导出」按钮生成 JSON（含日薪 / 月薪 / 预设 / 收入配置，v2 结构）或 CSV（带 BOM，Excel 直接打开）。
- **文件级备份**：直接复制 `data/works.db` 单文件即可完整备份；恢复时覆盖同名文件。
- **导入**：支持 JSON / CSV 合并导入（自动跳过重复）或覆盖导入（迁移恢复），兼容旧版仅含 `works` 数组的备份。

## 结论

数据库结构**清晰、克制、契合"本地单用户"定位**：模式隔离由表结构保证，索引精准不冗余，单例配置与待审查箱的设计兼顾了简单与安全，入参校验在应用层完备。唯一的可选加固是为枚举列增加数据库级 `CHECK` 约束，属锦上添花，不影响当前功能与数据正确性。
