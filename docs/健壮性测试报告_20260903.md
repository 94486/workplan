## 一、缺陷明细（供复核，均未修改代码）

### P1【高】NaN / Infinity 输入导致 HTTP 500（连接异常）

- **位置**：`backend/main.py`（缺失 `RequestValidationError` 自定义处理器；现有唯一 handler 是 404 兜底，约 70 行）
- **触发面**：`backend/models.py:21/23`（`duration_hours`、`expected_income` 等 float 字段带 `ge/le`）
- **复现**：
  ```bash
  curl -X POST http://127.0.0.1:8000/api/works -H "Content-Type: application/json" ^
    -d "{\"name\":\"nan\",\"planned_date\":\"2026-09-03\",\"duration_hours\":NaN}"
  # 期望 422，实际 500 / 连接被重置
  ```
  `Infinity`、`-Infinity` 同。
- **根因链**（uvicorn 日志 traceback 实锤）：
  1. `json.loads` 按 Python 扩展语法**接受** `NaN/Infinity`（非标准 JSON 但默认解析器不拒绝）；
  2. pydantic 校验 `NaN >= 0` 失败 → 正确抛出 `RequestValidationError`，错误上下文含 `input: nan`；
  3. FastAPI 默认处理器 `fastapi/exception_handlers.py:23` 构造 `JSONResponse` → Starlette `responses.py:183` 用 `json.dumps(allow_nan=False)` 序列化 → **`ValueError: Out of range float values` 二次异常** → 500。
- **影响**：任何外部工具（Python `json.dumps` 默认就会**写出** NaN）生成的数据打到 API 即触发；导入链路若复用同一解析也可能踩中。
- **建议修复方向（二选一，请复核）**：
  - A. 注册全局 `RequestValidationError` 处理器，对 `exc.errors()` 递归消毒非有限浮点（`math.isfinite` 检查后 `str()` 化）再返回 422；
  - B. 各模型 `model_config = ConfigDict(allow_inf_nan=False)`——**注意：这会让校验错误更早产生，但错误上下文仍携带 `input: nan`，默认处理器序列化时预计仍然 500**，故 B 单独使用可能不充分，需复核确认。

### P2【中】`PUT /api/monthly/settings` 部分提交会把未提交字段清零

- **位置**：`backend/routers/monthly.py:265-285`（`update_settings`），关键行约 279-281：
  `data.get("month_key","")`、`data.get("regular_income", 0.0)`、`data.get("other_income", 0.0)`
- **复现**（实测：原 regular=8000 → 提交后 0）：
  ```bash
  curl -X PUT http://127.0.0.1:8000/api/monthly/settings -H "Content-Type: application/json" -d "{\"other_income\": 3001}"
  ```
- **根因**：`model_dump(exclude_unset=True)` 只保留显式提交字段，但 UPSERT 对缺省字段直接取 0.0 覆盖，未读现有行做合并。
- **影响**：API 层数据丢失隐患。当前前端恰好全量提交所以未爆发；第三方对接或未来局部更新功能会踩中。
- **建议方向**：先 `_get_settings()` 取当前行，仅用 `data` 中出现的字段覆盖，再整行 UPSERT。

### P3【低/规范不一致】已完成的工作仍接受 PUT 修改计划字段

- **位置**：`backend/routers/works.py:90-107`（`update_work`）；**docstring（92 行）声称"待完成状态可改全部基础字段"，代码无任何状态检查**
- **复现**：complete 一条工作后 `PUT /api/works/{id} {"duration_hours":99}` → 200，计划=99 而实际=4，计划/实际语义漂移（统计页"平均工时/项"等口径受影响）。
- **建议方向**（业务决策，二选一）：a) 加 `if row["status"]=="done": raise HTTPException(409)`；b) 若允许改历史计划值，则修正 docstring 并在前端明示。

### P4【低/业务规则】`completed_date` 可填未来日期

- **位置**：`backend/models.py:62-75`（`WorkComplete` 仅 `date.fromisoformat` 格式校验）；`works.py:115` complete 无范围检查
- **复现**：`POST /api/works/{id}/complete {"completed_date":"2099-01-01"}` → 200
- **影响**：周/月统计出现"未来完成"，趋势图（近 8 周/近 6 月）不含该记录但看板归位到 2099 周。
- **建议方向**：若业务上"完成"应 ≤ 今天，在模型层加 `le=date.today()` 校验；否则文档明示允许补录/预录。

### P5【低】日期查询参数无格式校验

- **位置**：`works.py:46-48`（`date_from/date_to` 仅 `Query(None)`，无 pattern）；`monthly.py` 同类
- **实测**：`GET /api/works?date_from=乱写` → 200（SQLite 字符串比较，无报错无注入，良性但静默）
- **建议方向**：`Query(None, pattern=r"^\d{4}-\d{2}-\d{2}$")` 与 status/work_type 的枚举校验风格对齐。

### P6【观察项】非 /api 路径 404 一律回 index.html

- **位置**：`backend/main.py:70-80`（`@app.exception_handler(404)`）
- **现象**：请求不存在的 `/static/js/xxx.js` 返回 200 + index.html 内容（SPA 兜底副作用）。前端资源缺失时错误被掩盖成"脚本语法错误"，排查体验差。
- **建议方向**：兜底前判断 `not path.startswith("/static/")`。

## 二、代码质量评价

**规模**：后端 1850 行（6 路由 + models + database）、前端 2806 行 JS（7 模块）+ 2252 行 CSS + 156 行 HTML。零第三方前端依赖（自研 SVG 图表 charts.js），无上帝文件（最大 modal.js ~850 行，职责为各类弹窗尚属合理）。

**做得好的**：
1. **分层清晰**：routers（HTTP）/ models（校验）/ database（存储）职责不越位；`database.py` 短连接设计（每操作独立连接）在 10 并发写入测试下无锁死无丢失，与注释宣称一致。
2. **安全意识扎实**：全链路参数化 SQL（SQLi 字面量实测入库不执行）；前端三套 `esc()` 均转义 `& < > " '` 五字符，属性上下文安全，XSS 探针在看板/列表/弹窗均以纯文本渲染；push 对接鉴权用 `secrets.compare_digest` 常量时间比较（多数同规模项目不会做这步）；默认仅监听 127.0.0.1。
3. **校验密度高**：长度/枚举/数值范围/日期格式在 pydantic 层统一收口，实测 101 字符、2001 字符、`2026-02-30`、`2026-9-3`、负数、越上限全部 422；全空格名在 `_strip_name` 拦截。
4. **幂等与容错设计**：重复 complete 不覆盖实际值（`_fallback` 逻辑有意为之且有注释）、reopen 幂等、导入坏值行计入 invalid 不入库、二进制垃圾文件返回人话 400。
5. **中文注释质量罕见地高**：schema 每列带注释、设计要点写在模块头、打包路径陷阱（_MEIPASS 丢数据）有专门说明。

**短板**：
1. **零自动化测试**：仓库无 pytest/单测（本次两份脚本是外部补位）；`RequestValidationError→500` 这类问题一个 5 行的 TestClient 用例就能拦住。
2. **错误处理有盲区**：P1 即缺全局校验异常处理器；导入接口对超大文件无体积上限（本地单机场景风险低，但 Docker 部署值得考虑）。
3. **文档字符串与实现漂移**（见 P3）——注释整体优秀，恰恰说明个别失准处应修。
4. SQLite 无显式 `busy_timeout`（默认 5s 兜底，并发测试通过，属"恰好没事"而非"设计保证"）。

**总评**：以个人项目标准是**明显高于平均线的工程**——分层、校验、转义、鉴权、幂等都有意识有落地；主要欠的是测试基建和几个边界收口。综合评分：**B+（结构 A-，健壮性 B-，测试覆盖 D）**。

## 附录：P1–P6 修复进展（2026-09-15 核对）

以下对照原始缺陷逐项核对源码（`backend/main.py`、`backend/routers/{works,monthly,push}.py`、`backend/models.py`），确认已全部修复；回归验证由 `tools/_verify_fixes.py`（17 项，P1–P6 修复回归）持续覆盖。

| 编号 | 原缺陷 | 修复位置 | 修复方式 |
|---|---|---|---|
| P1【高】 | NaN / Infinity 输入导致 HTTP 500 | `backend/main.py` | 注册全局 `RequestValidationError` 处理器，`_sanitize_errors()` 递归消毒非有限浮点（`math.isfinite` 检查后 `str()` 化）再返回 422，杜绝序列化二次异常 |
| P2【中】 | `PUT /api/monthly/settings` 部分提交清零未提交字段 | `backend/routers/monthly.py` `update_settings` | 改为合并语义：仅覆盖显式提交字段，缺省字段读取现有行保留原值（部分更新不清零） |
| P3【低】 | 已完成的工作仍接受 PUT 修改计划字段 | `backend/routers/works.py` `update_work` | 采用原报告建议方向 b：修正 docstring 为「支持补录：已完成/待完成均可修改计划类基础字段，实际值不受影响」，业务语义明确（允许补录历史计划值） |
| P4【低】 | `completed_date` 可填未来日期 | `works.py complete_work` / `monthly.py complete_work` | 增加「完成日期不能晚于今天」校验，违规返回 422，防统计口径漂移 |
| P5【低】 | 日期查询参数无格式校验 | `works.py` / `monthly.py` `list_works`、`push.py _query_date` | 查询参数加 `pattern=r"^\d{4}-\d{2}-\d{2}$"` + `date.fromisoformat` 双重校验，非法返回 422 |
| P6【观察】 | 非 /api 路径 404 一律回 index.html | `backend/main.py` `not_found_handler` | 兜底前判断路径：`/api` 与 `/static` 前缀返回 JSON 404，其余路径才回 index.html（SPA 兜底） |

**修复后行为变化**：
- NaN / Infinity 推送或导入不再导致服务 500，统一以 422 返回并提示；
- 月薪收入配置部分更新（如只改 `other_income`）不会再清空 `regular_income` 与 `month_key`；
- 完成日期晚于今天被拒绝（422），未来完成不再进入统计口径；
- 日期查询参数乱写返回 422 而非静默放行；
- 前端静态资源缺失时返回真实 404，便于排查（不再被 SPA 兜底掩盖成脚本语法错误）。
