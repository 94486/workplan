# 架构设计

## 1. 总体架构

本项目采用「前端单页应用 + 后端 REST API + 本地 SQLite」的三层架构，后端同时负责托管前端静态资源，因此整个产品只需一个进程即可运行。

```
┌─────────────────────────────────────────────────────┐
│                    浏览器（前端 SPA）                  │
│  kanban.js  stats.js  list  ──►  视图层              │
│        │              │                              │
│        └────  Store（单一数据源 + 订阅通知） ──┐        │
│                     │                        │        │
│                    api.js（fetch 封装）       │        │
└─────────────────────┬───────────────────────┘        │
                      │ HTTP / JSON                    │
┌─────────────────────▼───────────────────────┐        │
│            FastAPI 后端（单进程）               │        │
│  routers/works.py   routers/stats.py   routers/data_io.py │ │
│  models.py（参数校验）  main.py（入口/静态）     │        │
│                     │                        │        │
│              database.py（短连接封装）          │        │
└─────────────────────┬───────────────────────┘        │
                      ▼                                │
              ┌───────────────┐                        │
              │  SQLite 文件   │ ◄──── 所有写操作后      │
              │ data/works.db │      Store.refresh()   │
              └───────────────┘      触发全视图重渲染    │
```

**实时同步机制**：所有写操作（增删改、完成、重开）成功后统一调用 `Store.refresh()` 重新拉取全量数据，再通过订阅者模式通知看板、统计、列表三个视图重绘 —— 保证「所有数据修改后报表实时同步更新」。

## 2. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 后端框架 | FastAPI | 类型校验（Pydantic）、自动 OpenAPI 文档、轻量、生态成熟 |
| Web 服务器 | Uvicorn | FastAPI 官方推荐，单进程即可承载个人使用 |
| 数据库 | SQLite（标准库 sqlite3） | 零安装、单文件、本地优先，适合个人工具 |
| 前端 | 原生 HTML/CSS/JS | 零构建、零依赖，易维护，离线可用 |
| 图表 | 自绘 SVG | 不依赖 CDN，暗色主题统一，离线可用 |
| Docker | python:3.11-slim | 镜像体积小，数据卷持久化 |
| Windows exe | PyInstaller | 单文件分发，内置静态资源 |

## 3. 数据模型

表 `works`（SQLite）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER PK | 自增主键 |
| name | TEXT | 工作名称（必填） |
| work_type | TEXT | `regular` 常规工作 / `other` 其他工作 |
| duration_hours | REAL | 花费时长（计划，小时） |
| planned_date | TEXT | 计划完成日期 `YYYY-MM-DD` |
| expected_income | REAL | 预期收入（元） |
| notes | TEXT | 备注 |
| status | TEXT | `pending` 待完成 / `done` 已完成 |
| actual_duration_hours | REAL | 实际花费时长（完成时回填） |
| completed_date | TEXT | 完成日期（完成时回填） |
| actual_income | REAL | 实际收入（完成时回填） |
| created_at / updated_at | TEXT | 创建 / 更新时间 |

**状态流转**：

```
                标记完成 complete(可带实际字段)
  pending  ───────────────────────────────►  done
      ▲                                         │
      └────────── 重新打开 reopen（清空实际字段） ─┘
```

**统计口径**（重要）：所有工时/收入统计**只取已完成工作的实际数据**（`actual_duration_hours` / `actual_income`），避免预期值与实际值混算。

## 4. 后端设计

- **database.py**：每次操作短连接（开-用-关），规避多线程共享连接问题；`WORK_DB_PATH` 环境变量控制数据位置；`init_db()` 幂等初始化，可选写演示数据。
- **routers/works.py**：工作 CRUD。`complete` 接口支持部分提交实际字段，回退优先级为「本次提交 → 已有实际值（已完成工作）→ 计划值/今天」，重复调用不会把已填实际值覆盖回计划值；`reopen` 清空实际字段恢复待完成。
- **routers/stats.py**：三个聚合接口，全部在 SQL 层完成 SUM/COUNT，后端只做格式化，保证口径一致。每周/每日统计均按 `completed_date` 归属，修改完成日期后数据自动迁移。
- **routers/data_io.py**：数据导入导出。导出 JSON / CSV；导入时对「已完成」工作做归一化（缺完成日期回退计划日期、缺实际值回退计划值），确保导入数据计入统计。
- **main.py**：入口 + 静态托管；打包（frozen）时自动打开浏览器；静态目录在源码模式指向 `frontend/`，打包模式指向 `_MEIPASS/frontend`。

## 5. 前端设计

模块划分（`frontend/js/`）：

| 模块 | 职责 |
| --- | --- |
| api.js | 所有 REST 调用的封装，业务层不直接写 fetch |
| store.js | 全局单一数据源 + 订阅发布；提供 `worksOn(date)`、逾期判定等查询工具 |
| charts.js | 零依赖 SVG 图表（双轴组合图：柱状+折线趋势、迷你构成图、分组柱状图、环形图、完成率环），带渐变填充与发光滤镜的科技感风格 |
| kanban.js | 日程看板：周视图 / 月视图切换与翻页；周/月汇总条；逾期徽章；悬浮一键完成；月视图「+N 更多」跳转周视图；卡片点击 → Modal 操作 |
| stats.js | 统计看板：分类报表卡 + 副指标卡（完成率/本周工时/本周收入/逾期）+ 近 8 周双轴趋势图 + 上月/今年至今期间面板（含常规/其他迷你构成图） |
| modal.js | 新建 / 编辑 / 完成 / 删除确认四种弹窗；Toast |
| app.js | 启动编排、Tab 切换（含 hash 路由与 `?view=month/week` 参数）、全部工作表格（表头排序、汇总行、逾期高亮）与筛选 |

**看板归位规则**：`Store.worksOn(date)` 中，待完成工作按 `planned_date`、已完成工作按 `completed_date` 匹配 —— 这就是「修改完成日期后工作自动跳转至对应日期」的实现点。

**双视图实现**：
- `viewMode` 状态控制渲染分支；`renderWeek()` 生成 7 列横向看板，`renderMonth()` 生成 6×7 日历网格（从当月 1 号所在周的周一开始）。
- 翻页逻辑与视图联动：周视图 ±7 天，月视图 ±1 个月；切换视图时保留当前锚点日期。
- 月视图每格最多显示 3 张卡片，超出显示 `+N 项更多`，点击后自动切换为周视图并定位到该周。

**视觉区分**：
- 常规工作 → 青色（左侧光条 + 标签）；其他工作 → 粉色（左侧光条 + 标签）
- 待完成 → 实线边框；已完成 → 半透明 + 虚线边框 + 删除线 + ✓ 徽标

## 6. 可维护性设计

- **单一数据源**：任何视图不自行持有数据副本，全部来自 Store，杜绝各视图数据不一致。
- **关注点分离**：API 封装 / 状态 / 渲染 / 交互各自独立模块，单文件职责单一。
- **后端参数强校验**：Pydantic 统一校验类型、范围、日期格式，前端可信任返回结构。
- **统计口径收敛**：统计 SQL 集中在 stats.py，避免多处分叉。
- **零第三方前端依赖**：不引入框架与构建链，升级与排障成本低。
